# CyberJobHunter

[English](README.md) | [Español](Readme_esp.md)

CyberJobHunter es un proyecto personal, educativo y no comercial desarrollado por un estudiante de Ingeniería Informática. Descubre y organiza prácticas y oportunidades junior de ciberseguridad, principalmente en Barcelona, Mataró y Badalona.

El proyecto combina un buscador en Python, almacenamiento persistente en Supabase PostgreSQL, un panel web local en español y automatización mediante GitHub Actions.

## Funcionalidades

- Descubrir ofertas mediante la API de Tavily con búsquedas predefinidas.
- Normalizar resultados, puntuar su relevancia mediante reglas de palabras clave y asignar prioridad alta, media o baja.
- Guardar ofertas en PostgreSQL y omitir URLs duplicadas con `ON CONFLICT (url) DO NOTHING`.
- Gestionar ofertas desde el panel local o el menú interactivo de terminal existente.
- Consultar todas las ofertas o filtrar por estado; buscar en títulos y descripciones, filtrar por prioridad y ordenar por prioridad, relevancia o fecha de detección.
- Revisar 25 ofertas por página, abrir su detalle y seguir el enlace original.
- Cambiar o recuperar cualquiera de los cuatro estados: `nueva`, `revisada`, `descartada` y `solicitada`.
- Ver contadores por estado y alternar entre tema claro y oscuro; el navegador recuerda el tema.
- Usar un diseño adaptable, controles accesibles por teclado y detalle a pantalla completa en pantallas pequeñas.
- Iniciar con doble clic en Windows o ejecutar búsquedas manualmente y mediante GitHub Actions.

Abrir una oferta no cambia su estado. Marcarla como solicitada no envía una candidatura a la empresa.

## Tecnologías y arquitectura

| Tecnología | Función |
| --- | --- |
| Python 3.13 | Búsqueda, puntuación, terminal y servidor local |
| Tavily (`tavily-python`) | Descubrimiento de ofertas |
| Supabase PostgreSQL | Almacenamiento persistente compartido |
| `psycopg[binary]` | Conexión directa con PostgreSQL |
| Flask | Panel local y API HTTP |
| HTML, CSS y JavaScript | Interfaz sin Node ni compilación |
| `python-dotenv` | Configuración local al iniciar la aplicación |
| `unittest` | Pruebas automatizadas sin servicios externos |
| `pip-audit` | Comprobación de vulnerabilidades conocidas en dependencias |
| GitHub Actions | Búsquedas, pruebas y auditorías automatizadas |

`main.py` busca y puntúa ofertas. `database.py` proporciona la conexión, las consultas y las actualizaciones de estado compartidas. `frontend.py` sirve el panel y utiliza esa capa de datos. El navegador no conecta directamente con Supabase ni recibe credenciales de la base de datos. Tavily se inicializa únicamente cuando empieza una búsqueda; el panel no llama a Tavily.

Importar los módulos de la aplicación no carga `.env`. Ejecutar el punto de entrada normal de la terminal o del panel carga la configuración local del proyecto.

## Instalación

### 1. Clonar y crear el entorno

```bash
git clone https://github.com/promoxif/CyberJobHunter.git
cd CyberJobHunter
python -m venv .venv
```

Se utiliza Python 3.13 para el desarrollo. Instala las dependencias en Windows:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

En Linux/macOS:

```bash
.venv/bin/python -m pip install -r requirements.txt
```

Las versiones de dependencias directas están fijadas en `requirements.txt`; las herramientas de desarrollo figuran en `requirements-dev.txt`.

### 2. Configurar las credenciales

Crea tu propia [clave de Tavily](https://app.tavily.com/) y un [proyecto de Supabase](https://supabase.com/). Crea un `.env` privado en la raíz del proyecto:

```dotenv
TAVILY_API_KEY=your_tavily_api_key
DATABASE_URL=your_supabase_postgresql_connection_string
```

Utiliza la cadena de conexión PostgreSQL adecuada para tu red, como el session pooler, y sustituye su marcador de contraseña de forma privada. El panel necesita `DATABASE_URL`; las búsquedas utilizan `TAVILY_API_KEY`. Las variables de entorno ya definidas tienen prioridad sobre los valores de `.env`.

Nunca subas `.env`, contraseñas ni claves API al repositorio. Cada ordenador necesita su propia configuración privada.

### 3. Crear la tabla en una instalación nueva

Ejecuta esto en el editor SQL de Supabase si la tabla todavía no existe:

```sql
CREATE TABLE IF NOT EXISTS ofertas (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    titulo TEXT NOT NULL,
    url TEXT NOT NULL UNIQUE,
    descripcion TEXT,
    puntuacion_relevancia INTEGER,
    prioridad TEXT,
    fecha_detectada TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    estado TEXT NOT NULL DEFAULT 'nueva'
);
```

El panel utiliza este esquema existente y no requiere migración. Crear la tabla no configura por sí solo una exposición segura mediante la API ni sus permisos; revisa el apartado de seguridad.

## Iniciar el panel

### Windows: doble clic

Tras la instalación, haz doble clic en **`Iniciar CyberJobHunter.bat`**. Inicia el servidor local y abre el navegador automáticamente. Mantén la ventana de terminal abierta mientras utilizas el panel; ciérrala o pulsa `Ctrl+C` para detener el servidor.

Para crear un acceso directo: clic derecho en el lanzador → **Mostrar más opciones → Enviar a → Escritorio (crear acceso directo)**. Conserva el lanzador original dentro de la carpeta del proyecto.

### Iniciar desde la terminal

Desde la carpeta del proyecto en Windows:

```powershell
.\.venv\Scripts\python.exe frontend.py
```

Para abrir también el navegador automáticamente:

```powershell
.\.venv\Scripts\python.exe frontend.py --open-browser
```

En Linux/macOS utiliza `.venv/bin/python frontend.py`. Abre **http://127.0.0.1:5000** con esa dirección exacta, en lugar de `localhost`.

Si el puerto está ocupado, detén la otra instancia antes de iniciar otra. Si el navegador se abre antes de que termine de arrancar el servidor, recarga la página.

### PC y portátil

Ejecuta un servidor local independiente en cada equipo, con dependencias y configuración privada instaladas en ambos. Comparten la misma base de datos de Supabase y no necesitan conectarse entre sí.

Pulsa **Actualizar ofertas** para obtener cambios realizados desde otro equipo o por GitHub Actions. No hay sincronización automática ni modo sin conexión. Si dos dispositivos modifican la misma oferta, prevalece el último cambio guardado.

El panel muestra inicialmente las ofertas nuevas, ordenadas por prioridad, relevancia y fecha de detección descendentes. Cambiar filtros reinicia la paginación. Los cambios de estado actualizan el listado y los contadores después de que el servidor confirme el guardado.

## Terminal y automatización de búsquedas

Con el entorno virtual activado:

```bash
python main.py
python main.py --auto
```

El primer comando abre el menú interactivo; el segundo realiza una búsqueda sin interacción. También puedes utilizar directamente el ejecutable de Python del entorno, como en los comandos del panel anteriores.

El workflow `.github/workflows/buscar_ofertas.yml` instala dependencias y ejecuta `python main.py --auto`. Su programación está configurada para las **09:15 Europe/Madrid cada día**; las ejecuciones programadas pueden retrasarse. Puedes iniciarlo manualmente desde **Actions → CyberJobHunter - Daily Search → Run workflow**.

Configura estos secretos del repositorio en **Settings → Secrets and variables → Actions**:

| Secreto | Función |
| --- | --- |
| `TAVILY_API_KEY` | Búsquedas de Tavily |
| `DATABASE_URL` | Conexión PostgreSQL |

El workflow tiene permisos de solo lectura sobre el repositorio, un límite de 15 minutos por trabajo y control de concurrencia para evitar búsquedas solapadas en el mismo grupo. Las ofertas persisten en Supabase entre ejecuciones. Consulta la salida del workflow para saber cuántas ofertas nuevas se han guardado. El panel solo gestiona ofertas almacenadas; no inicia búsquedas.

## API HTTP local

Estos endpoints están destinados al panel local, no al alojamiento público:

| Método y ruta | Función |
| --- | --- |
| `GET /` | Panel e inicialización de la sesión CSRF |
| `GET /api/ofertas` | Ofertas y total filtrado; parámetros: `estado`, `prioridad`, `q`, `orden`, `pagina` |
| `GET /api/ofertas/<id>` | Detalle de la oferta |
| `GET /api/estadisticas` | Contadores globales por estado y total |
| `PATCH /api/ofertas/<id>/estado` | Guardar exactamente un campo: `{"estado": "revisada"}` |

Los órdenes permitidos son `prioridad`, `relevancia` y `recientes`. Cada página contiene 25 ofertas. Los cambios requieren el Origin local y el `X-CSRF-Token` de la sesión; las peticiones GET no modifican registros.

## Seguridad y limitaciones

### Controles implementados

- Servidor restringido a `127.0.0.1:5000`, con validación estricta de host y puerto, modo de depuración y consola interactiva desactivados.
- Sin CORS; se rechazan peticiones entre sitios y los cambios de estado requieren validación de Origin y token CSRF.
- Cookies de sesión CSRF HTTP-only y SameSite Strict. Reiniciar el servidor invalida las sesiones existentes; recarga las pestañas antiguas si se bloquea un cambio. Estas sesiones no son autenticación.
- SQL parametrizado, valores permitidos para filtros, órdenes y estados, rechazo de campos adicionales al actualizar y modificaciones limitadas a la columna `estado`.
- Búsquedas de hasta 200 caracteres, cuerpos de petición de hasta 4 KiB y páginas numeradas del 1 al 100000.
- Tiempo máximo de conexión a la base de datos de 10 segundos y límite de 10 segundos por sentencia SQL.
- Contenido de ofertas renderizado como texto. Solo se ofrecen enlaces HTTP/HTTPS validados y sin credenciales; los enlaces originales se abren con `noopener noreferrer`. El servidor no descarga sus páginas.
- Recursos locales sin analítica, scripts externos, fuentes remotas ni CDN. Content Security Policy restrictiva, bloqueo de marcos, `nosniff`, `no-referrer`, permisos restringidos del navegador y respuestas `no-store`.
- Solo se sirven los recursos estáticos designados; la raíz del repositorio y los archivos privados no se exponen por HTTP.
- Las credenciales permanecen en Python. Los errores del panel no devuelven detalles de excepciones ni cadenas de conexión. Los registros de acceso HTTP se desactivan al iniciar mediante `frontend.py` para evitar guardar términos de búsqueda.
- `.gitignore` excluye variantes de `.env`, copias comunes de bases de datos, registros y archivos locales de pruebas. No elimina secretos ya guardados en el historial de Git.

### Límites y comprobaciones pendientes

**No hay inicio de sesión.** Una persona o programa con acceso a tu sesión del sistema operativo puede utilizar el panel. Estos controles no protegen contra malware, extensiones maliciosas del navegador ni un dispositivo comprometido. Mantén el servidor local; no lo expongas mediante túneles, proxies o una interfaz de red.

El tráfico HTTP del panel permanece en loopback. El tráfico remoto con PostgreSQL utiliza TLS con `sslmode=require`; esto exige cifrado, pero no garantiza por sí solo la verificación completa del certificado y del nombre del servidor. Utilizar `verify-full` requiere configurar el certificado raíz de confianza adecuado. Esa configuración no se ha cambiado aquí.

**Queda por verificar la configuración de Supabase:** privilegios del usuario de conexión, acceso con permisos mínimos, Row Level Security (RLS), permisos de `anon`/`authenticated` y exposición de la tabla mediante Data API. La configuración remota no se ha auditado ni modificado como parte de la implementación del panel. Que la conexión funcione no demuestra que estos permisos estén correctamente restringidos. Consulta la [guía de protección de datos de Supabase](https://supabase.com/docs/guides/database/secure-data).

El frontend está integrado con Supabase mediante `database.py`; cuando lo inicias, carga tu configuración y utiliza la base de datos real. Las comprobaciones de desarrollo utilizaron datos ficticios y conexiones simuladas, sin cargar `.env` ni escribir en Supabase.

Las comprobaciones de dependencias detectan vulnerabilidades conocidas y publicadas, no todos los fallos posibles. No se garantiza la ausencia absoluta de fugas. Revoca y sustituye cualquier credencial que se exponga.

### Limitaciones de las ofertas

La relevancia es una puntuación de reglas, no un modelo de IA ni un porcentaje de afinidad. La fecha de detección no es la de publicación. Las descripciones pueden ser fragmentos del buscador y no anuncios completos. Empresa, salario y ubicación no se guardan como campos independientes. La cobertura, actualidad y exhaustividad dependen de Tavily; su API puede tener cuotas o costes.

## Pruebas y mantenimiento

En Windows:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip_audit -r requirements.txt
```

Utiliza `.venv/bin/python` en Linux/macOS. Las pruebas usan repositorios ficticios o conexiones simuladas, sin cargar `.env`, llamar a Tavily ni escribir en Supabase. Cubren filtros, paginación, cambios de estado, puntuación y deduplicación, parámetros SQL, validación de peticiones, CSRF, orígenes, hosts, rutas privadas, enlaces inseguros, cuerpos excesivos y errores sin información sensible.

Para la revisión visual, detén el panel real y ejecuta:

```powershell
.\.venv\Scripts\python.exe tests/preview_fixture.py
```

Esta vista previa utiliza datos explícitamente ficticios y no carga configuración privada.

`.github/workflows/seguridad.yml` ejecuta pruebas y `pip-audit` en push, pull request, ejecución manual y semanalmente los lunes a las 08:30 UTC. Utiliza permisos de solo lectura sobre el repositorio y no requiere secretos. Actualiza dependencias de forma deliberada y repite las pruebas y la auditoría antes de adoptar nuevas versiones.
